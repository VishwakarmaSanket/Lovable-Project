What are we actually building?
Start with the job of each layer before learning its API
Core concept

Our browser terminal is not one thing. It is a chain of components. The browser draws a terminal and captures keystrokes; the backend owns a real interactive shell through a pseudo-terminal; Socket.IO carries bytes/events between them; the router gets the connection to the right sandbox.

01
Terminal fundamentals
stdin, stdout, stderr, shell, process — the pieces underneath the UI
Core concept

A terminal is an interface through which a user interacts with a command-line program. A shell such as bash is the program interpreting commands. The terminal UI and the shell are related, but they are not the same thing.

Input and output

Stream / componentSimple meaningIn our system
stdinInput supplied to a process.Keyboard data ultimately reaches the shell through the PTY.
stdoutNormal output from a process.PTY output is forwarded to the browser.
stderrDiagnostic/error output.It can appear in the terminal stream just like other terminal output.
shellProgram that parses commands and starts processes.The agent defaults to bash unless SHELL is set.
processA running program with its own execution context.The shell is a process; commands such as npm can create more processes.

Why a normal child process is not always enough

If a backend simply starts a command and pipes stdin/stdout, basic commands can work. Interactive programs, however, often care about terminal characteristics: cursor movement, terminal dimensions, line editing, control characters, colors, full-screen interfaces, and signals.

ApproachLimitation / behaviorTerminal experience
Plain process + pipesGood for simple non-interactive command execution.Not a complete terminal environment.
PTYProvides a pseudo-terminal interface.Much closer to an actual interactive shell.
⚠️

Do not memorize “terminal = shell.” The shell is a process. The terminal is the interaction environment. Our architecture deliberately separates the browser terminal emulator from the backend shell.

02
TTY vs PTY
The concept that explains why node-pty exists
Core concept

TTY historically refers to a terminal device/interface. A PTY is a pseudo-terminal: software creates a terminal-like endpoint for a program, allowing another program to interact with that process as though it were attached to a terminal.

The useful mental model

Terminal emulatorxterm.js in browser
↔
PTYnode-pty
↔
Shellbash

The PTY is the bridge that makes the shell behave like it is attached to an interactive terminal rather than just being a detached process with simple pipes.

Why terminal size matters

A terminal has rows and columns. Programs can use that information for wrapping, layouts, prompts, and full-screen interfaces. Our agent initially creates the PTY with cols: 80 and rows: 30.

Project · sandbox/agent/src/app.js
// Spawn the PTY process
const ptyProcess = pty.spawn(shell, [], {
    name: 'xterm-color',
    cols: 80,
    rows: 30,
    cwd: "/workspace",
    env: process.env
});
Source: sandbox/agent/src/app.js at commit 3505dcca.
03
node-pty
The backend component that owns the interactive shell
Core concept

node-pty is the project dependency used to create the pseudo-terminal process. In this project the agent selects a shell, spawns it inside /workspace, receives its output, and writes user input back into it.

Step 1 — Select the shell

Project code
const shell = process.env.SHELL || 'bash';

There are two possibilities: use the SHELL environment variable, or fall back to bash.

Step 2 — Spawn the PTY

Project code
const ptyProcess = pty.spawn(shell, [], {
    name: 'xterm-color',
    cols: 80,
    rows: 30,
    cwd: '/workspace',
    env: process.env
});
OptionMeaning in this project
shellExecutable to start, normally bash.
[]No explicit shell arguments are supplied here.
nameTerminal type identifier: xterm-color.
cols / rowsInitial terminal dimensions.
cwdShell starts in the shared workspace: /workspace.
envPasses the agent process environment into the shell.

Step 3 — Read PTY output

Project code
ptyProcess.onData((data) => {
    io.emit('terminal-output', data);
});

This is the backend half of the output path: shell → PTY → Socket.IO event → browser.

Step 4 — Write user input

Project code
socket.on('terminal-input', (data) => {
    ptyProcess.write(data);
});

This is the reverse path: browser keyboard → Socket.IO event → PTY → shell.

💡

Key insight — the agent does not manually parse commands such as ls. It writes the user's terminal data into the PTY. The shell receives that input and decides what it means.

04
xterm.js
The browser-side terminal emulator
Core concept

xterm.js is a terminal emulator implemented in JavaScript. In our React frontend it renders the terminal, handles keyboard interaction, writes received terminal data to the screen, and provides addons for fitting the terminal to its container and detecting web links.

Project dependencies

frontend/package.json

"@xterm/addon-web-links": "^0.12.0",

Creating the terminal

  fontFamily: '"JetBrains Mono", "Fira Code", monospace',

Two methods you must remember

APIDirectionMeaning in our terminal
term.onData()Browser → backendUser typed something; send it to Socket.IO.
term.write()Backend → browserPTY produced output; render it in xterm.js.
The two directions
// keyboard → server
term.onData((data) => {
  socket.emit('terminal-input', data);
});

// server → terminal screen
socket.on('terminal-output', (data) => {
  term.write(data);
});
⚠️

Do not reverse these in your mental model. onData() observes user input. write() writes output into the terminal emulator.

05
Socket.IO bridge
Turning browser events into PTY input and PTY output into browser events
Core concept

The project uses Socket.IO for the terminal connection. The important abstraction is an event channel: the client emits terminal-input; the server emits terminal-output.

Browser connection

Terminal.jsx
const agentHost = `http://${sandboxId}.agent.localhost`;

const socket = io(agentHost, {
  transports: ['websocket', 'polling'],
  reconnectionAttempts: 5,
  reconnectionDelay: 1000,
});

Server connection

sandbox/agent/src/app.js
const io = new Server(httpServer, {
  cors: {
    origin: "*",
    methods: ["GET", "POST", "PATCH"],
  }
});

io.on("connection", (socket) => {
  socket.on("terminal-input", (data) => {
    ptyProcess.write(data);
  });
});

Why not just send HTTP requests?

A terminal is continuous and interactive. A user can type one character, receive output, type another character, press Ctrl+C, receive a prompt, start a program, and continue interacting. A persistent bidirectional connection fits that pattern better than one HTTP request per keystroke.

💡

Project wording — the codeSpace documentation describes the terminal as “xterm.js terminal connected via Socket.IO” and the router as handling WebSocket upgrades for Socket.IO terminal traffic.

06
Router & WebSocket path
How the connection reaches the correct per-sandbox agent
Core concept

The browser connects to a sandbox-specific hostname such as {sandboxId}.agent.localhost. The router extracts the sandbox ID from the host and proxies the request/upgrade to the matching Kubernetes service.

Browserid.agent.localhost
→
Ingress / Routerhost → sandboxId
→
K8s Servicesandbox-service-{id}
→
Agentport 3000

HTTP and upgrade handling

The router creates normal HTTP proxy middleware for sandbox traffic and a shared httpxy proxy server for WebSocket upgrades.

sandbox/router/src/app.js
const wsProxy = createProxyServer({ changeOrigin: true });

server.on('upgrade', (req, socket, head) => {
  const host = req.headers.host;
  const sandboxId = host.split('.')[0];
  const type = host.split('.')[1];

  if (type === 'agent') {
    wsProxy.ws(
      req, socket,
      { target: `http://sandbox-service-${sandboxId}:3000` },
      head
    );
  }
});
⚠️

This area was a real project debugging point. The repository change log records that the router had to move away from an incorrect WebSocket upgrade approach and use a shared httpxy proxy server with .ws().

That matters because terminal traffic is not useful if the browser can connect to the router but the upgrade never reaches the agent.

07
End-to-end terminal lifecycle
Follow one character from your keyboard to bash and back
Core concept

If you can explain this lifecycle without looking at the code, you understand the terminal implementation.

1. React mounts Terminal
The component creates an xterm.js instance and fits it to its container.
2. Browser connects to the agent hostname
Socket.IO connects to http://{sandboxId}.agent.localhost.
3. Router receives the connection
The sandbox ID is derived from the hostname and traffic is proxied to the corresponding sandbox service.
4. Agent has already spawned bash through node-pty
The PTY starts in /workspace with the configured environment and initial dimensions.
5. User presses a key
xterm.js emits data through term.onData().
6. Socket.IO emits terminal-input
The raw terminal data is sent to the agent.
7. Agent writes into the PTY
ptyProcess.write(data) feeds the data to the interactive shell.
8. Shell executes / responds
bash interprets the input and produces terminal output.
9. Output travels back
PTY onData → Socket.IO terminal-output → xterm.js term.write() → pixels in the browser.
KEYSTROKE ↓ xterm.js term.onData() ↓ socket.emit('terminal-input') ↓ router / Socket.IO transport ↓ ptyProcess.write(data) ↓ bash ↓ ptyProcess.onData(data) ↓ io.emit('terminal-output', data) ↓ socket.on('terminal-output') ↓ term.write(data) ↓ SCREEN

One-minute self-test

  1. If I type pwd, which component first sees the keyboard data? xterm.js.
  2. Which function forwards that data from xterm.js? term.onData().
  3. Which Socket.IO event carries it? terminal-input.
  4. What does the agent do with it? ptyProcess.write(data).
  5. Who interprets pwd? The shell.
  6. How does output return? PTY → onData → terminal-output → term.write.
11
Interview drill
Answer these in your own words before reading the reference answer

Q1 — Why did we use node-pty?

Reference answer

Because the backend needs an interactive pseudo-terminal attached to a shell. The terminal should behave like a real interactive shell rather than just a one-shot command executor. node-pty creates that PTY-backed process and gives the application input/output hooks.

Q2 — Is xterm.js executing commands?

Reference answer

No. xterm.js is the browser-side terminal emulator. It renders terminal output and captures user input. The actual command execution occurs in the sandbox through the shell attached to the PTY.

Q3 — Why use Socket.IO?

Reference answer

The terminal is a long-lived, interactive, bidirectional stream of user input and process output. Socket.IO gives the project a persistent connection with named events such as terminal-input and terminal-output.

Q4 — What does the router do?

Reference answer

The router is the traffic-distribution layer. It reads the sandbox ID from the hostname and proxies HTTP and WebSocket traffic to the corresponding per-sandbox Kubernetes service. It is not the process executing shell commands.

Q5 — Explain the complete architecture in 30 seconds.

Reference answer

The React frontend uses xterm.js as the terminal emulator. When the user types, xterm.js emits the data through Socket.IO. The router routes the sandbox-specific connection to the sandbox agent. The agent uses node-pty to run an interactive shell inside /workspace. Shell output comes back through the PTY, the agent emits it as a Socket.IO event, and xterm.js renders it.

Q6 — What is a PTY?

Reference answer

A PTY, or pseudo-terminal, is a software-created terminal interface that allows a process such as a shell to interact as though it were connected to a terminal. That is important for interactive command-line behavior.

Q7 — What would you inspect if the terminal connects but typing has no effect?

Reference answer

Trace the input path: term.onData() → Socket.IO terminal-input → agent socket handler → ptyProcess.write() → shell. Check each boundary rather than changing xterm styling or PTY creation blindly.
